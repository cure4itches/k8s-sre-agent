# PM-2026-001 · recommendationservice OOMKilled 반복으로 추천 영역 장애

- 문서 ID: PM-2026-001
- 발생일: 2026-07-08
- 심각도: SEV-3
- 영향 서비스: recommendationservice (사용자 영향: 상품 상세 페이지)
- 관련 Runbook: RB-01, RB-08
- 작성: SRE 팀 on-call 담당자

## 요약

상품 추천 로직 변경으로 recommendationservice의 메모리 사용량이 늘어났고, 기존 메모리 limit을 넘어 파드가 OOMKilled로 반복 재시작되었다. 메모리 limit 상향으로 복구했다.

## 영향

- 약 42분 동안 상품 상세 페이지의 추천 영역이 간헐적으로 비어 있었다.
- 일부 요청에서 frontend가 5xx를 반환했다. 주문 기능에는 영향이 없었다.

## 타임라인

- 14:05 추천 후보 수를 늘린 recommendationservice 신규 버전 배포
- 14:20 recommendationservice 파드 재시작 알람 발생 (15분간 재시작 3회 초과)
- 14:26 on-call 담당자 확인 시작. `kubectl describe pod`에서 `Reason: OOMKilled`, `Exit Code: 137` 확인
- 14:34 메모리 사용량이 재시작 직전마다 limit에 도달하는 패턴 확인
- 14:38 롤백과 limit 상향을 비교 검토. 추천 품질 개선이 필요한 변경이어서 limit 상향으로 결정
- 14:41 메모리 limit을 현재 값의 1.5배로 상향 (승인 후 실행)
- 14:47 새 파드 기동 완료, 재시작 중단 확인
- 14:52 5분간 메모리 사용률 limit 대비 0.7 수준 유지 확인, 복구 선언

## 근본 원인

- 추천 후보 수를 늘리면서 요청당 메모리 사용량이 약 40% 늘었으나, 배포 시 메모리 limit을 함께 조정하지 않았다.
- 부하 테스트 환경의 트래픽이 운영보다 적어 사전에 문제가 드러나지 않았다.

## 대응에서 잘된 점

- OOMKilled 판정이 빨랐다. 종료 사유와 메모리 추이를 함께 보고 limit 부족으로 바로 좁혔다.
- 롤백과 limit 상향을 비교한 뒤 결정해 기능 변경을 유지할 수 있었다.

## 아쉬운 점

- 알람 발생 후 확인 시작까지 6분이 걸렸다.
- 적절한 limit 값을 정하는 기준이 문서화되어 있지 않아 값을 정하는 데 시간이 걸렸다.

## 재발 방지 조치

- 메모리 사용률(limit 대비) 0.9 이상 지속 시 사전 알람 추가
- RB-08에 limit 값을 정하는 기준(최대 사용량의 1.3배와 현재 limit의 1.5배 중 작은 값) 추가
- 리소스 사용량이 바뀌는 변경은 배포 체크리스트에 limit 검토 항목 추가
